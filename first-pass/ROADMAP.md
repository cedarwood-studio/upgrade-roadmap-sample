## Review findings

The report below was generated by our tooling on November 13, 2026, and reviewed the same day. The review compared it with the Rails changelogs and with the Postal project's own upgrade branches, and found the following. Each one is also marked "added in review" at the stage it belongs to. The driver table and the estimate are as generated.

**Four lines the rules search missed.** Each is a change in Rails that our rules search didn't flag. The suite loads the first two files without running the lines in question: the coverage data shows zero hits on `lib/migration_waiter.rb:18` and on the method that starts a password reset. **One dependency to pin.** Active Support 7.1.6 and 8.0.5.2 pass a `quirks_mode` option to the `json` gem, and `json` 3.0.0 (September 2026) no longer accepts it according to its changelog. Every lock here holds `json` at 2.7.1, so nothing breaks today. Nothing pins it either, and the resolver's fallback, `bundle lock --update`, could raise it. Pin `json` below 3 until 8.1.

**Statements corrected in place.**

- The test baseline. The generated report said all 851 examples pass with the network on. Three examples that pass offline fail in that rerun, so no single run passes all 851.
- The 122 gems with no declared constraint. None of them depends on a Rails component, which the generated wording didn't say.
- The 40 files never loaded include one JavaScript manifest.
- The estimating rubric hasn't been calibrated against any completed upgrade. The generated report said "not more than one."

**Items in the plan that are aimed wrong.** We left them in place and note them here.

- S4, adapter registration. The per-server message databases use `Mysql2::Client` directly (`lib/postal/message_db/connection_pool.rb:65`) and don't go through an Active Record adapter. Only the main database is in question.
- S5, semicolon separators. The tracking middleware parses the query string with `Rack::Request` (`lib/tracking_middleware.rb:16`), and the locked Rack 3.2 already splits on `&` only. The change applies to controller parameters.
- S6, cache expiry and cache format. The application has no `Rails.cache` call in `app` or `lib`, so both are moot.
- S6, "won't boot." A `serialize` call with no coder raises when the model class loads. That's at boot in production, where classes load eagerly, and at first use in development and test.

**Things the plan could do earlier.** `show_exceptions = :none` and `coder: YAML` are both valid on Rails 7.1.6, so they can ship in S1 or S2 ahead of any hop.

**Not in the plan.** The Rails upgrade guide recommends running `bin/rails app:update` at each hop and adopting defaults through the generated `new_framework_defaults` file. The plan changes `load_defaults` directly and never runs `app:update`. Ruby 3.4.6 is above the floor for every hop (3.1 for Rails 7.2, 3.2 for 8.0 and 8.1), which the report didn't state.

## Summary

Postal's main branch pins Rails 7.1.6, which passed end of life 408 days ago, on Ruby 3.4.6, which is supported until March 2028. The target is 8.1.4.1, three series away (7.2, 8.0, 8.1), and both intermediate series are already past end of life too, so neither is a place to stop. The dependency resolver found a lock for every hop. One gem, `annotate`, a development tool, blocks the last two, and the resolver could only keep it by downgrading it from 3.2.0 to 2.6.5. Very little application code is touched by documented breaking changes: 6 lines across 5 rules, 4 of them executed by the test suite, and we read 2 of the 6 as not affected. The review found four more lines the rules didn't cover. The suite runs in a sandbox in 215.9 seconds: 851 examples, 834 passing with the network off. The other 17 pass once DNS is reachable, and three that pass offline fail then. We plan 9 stages and estimate 19.5 to 84.5 hours. The largest unknown is behavior the suite never reaches. Line coverage collected during the run shows 40 of 155 source files never loaded, 17 web controllers among them. A smaller one is the 122 dependencies that don't depend on Rails directly, so their gemspecs can't say whether they work on the newer versions.

## Test suite health

**It runs (measured).** `bundle exec rspec` ran in a clean sandbox with MariaDB and no other manual setup, configured from environment variables the way the project's CI does it. 851 examples in 215.9 seconds, none pending, no errors outside examples.

**Failures before any change (measured).** 17 examples failed with the network off: 16 in `spec/lib/dns_resolver_spec.rb` and 1 in `spec/senders/smtp_sender_spec.rb` (`spec/senders/smtp_sender_spec.rb:150`). They resolve real DNS names. Rerun with the network on, all 17 pass. In that rerun three other examples in `spec/lib/dns_resolver_spec.rb` fail. They expect a lookup to time out, they pass offline, and with the network on they got an answer. So the failures are environmental, every one of the 851 examples passes in one of the two runs, and no single run passes all of them. These examples depend on outside DNS answers, and a failure there during the upgrade may have nothing to do with Rails.

**Deprecation warnings (measured).** Zero Rails deprecation warnings, with the test environment set to print them to stderr (`config/environments/test.rb:40`). Zero is a fact about 7.1.6 only; the count on each hop is unknown until that hop runs. The harvest also isn't complete even on 7.1.6: `show_exceptions = false` at `config/environments/test.rb:28` was [deprecated in 7.1](https://guides.rubyonrails.org/7_2_release_notes.html#action-pack-removals) per our rules file, yet no warning for it showed up in the run. We infer some deprecations are raised in ways the harvest doesn't see.

**Ruby warnings (measured).** 5 distinct messages, 8 occurrences. Three are the app's own notices about test configuration. Two are in Ruby's deprecated category, and both come from gems, [webmock](https://rubygems.org/gems/webmock/versions/3.20.0) and [domain_name](https://rubygems.org/gems/domain_name/versions/0.6.20240107). Neither is on this path.

**Coverage (measured).** 83.7 percent of lines in the files the suite loaded, 4,349 of 5,198. The suite loaded 145 files, 115 of them in `app` and `lib` and 30 under `config`. The other 40 of the 155 source files in `app` and `lib` were never loaded. One of the 40 is a JavaScript manifest that Ruby coverage can't load, so in Ruby files it's 39 of 154:

- 17 controllers, which is most of the web interface. Examples: `app/controllers/servers_controller.rb`, `app/controllers/organizations_controller.rb`, `app/controllers/credentials_controller.rb`, `app/controllers/users_controller.rb`.
- 8 scheduled tasks under `app/scheduled_tasks`.
- The SMTP server and worker entry points, `app/lib/smtp_server/server.rb` and `app/lib/worker/process.rb`, and the health server.
- 3 models, the three spam and virus inspectors under `lib/postal/message_inspectors`, and a handful of utilities.

**Coverage of the affected lines (inferred, from a join of two measurements).** Of the 6 lines, 4 are executed by the suite: both serializer lines, the `after_commit` and the test configuration line. The other 2 are `bin/update` and `db/schema.rb`, files the suite doesn't load. No affected line sits in loaded code that the suite skips. "Executed" means the line ran, which is weaker than saying an assertion checks its result.

**What this means for parity (inferred).** For the mail pipeline, the models and the legacy API, the suite is a sound net: it runs offline in under four minutes and covers the loaded code well. It isn't enough on its own to hold "same behavior" for the whole app, because a Rails upgrade changes controllers, views, sessions and cookies first, and that's the part the suite doesn't load. Before any version changes we'd add:

- a recorded set of HTTP requests and responses for the web interface controllers and the legacy API, taken on 7.1.6;
- characterization tests for the scheduled tasks;
- a test that reads serialized `Credential` options and `WebhookRequest` payloads from rows written on 7.1.6;
- a test that a session cookie issued on 7.1.6 is still accepted;
- a boot check for the SMTP server and worker processes.

## Plan

Nine stages. The framework hops leave `load_defaults` at 7.0; the defaults move afterward, in their own stages. Hours are attended engineering hours. Every hop stage ships separately, but 7.2 and 8.0 are past end of life, so we'd move through them without pausing longer than it takes to watch a deploy.

### S1: Record the baseline on Rails 7.1.6

- **Goal:** Fix the reference behavior every later stage is compared against, and add tests where the suite doesn't reach.
- **Changes:**
  - Store the 851 example ids and their status as the reference set. Run the two DNS-dependent files with the network on, as CI does (`.github/workflows/ci.yml:58`), and record which examples pass there (`baseline.json`).
  - Assemble a recorded HTTP request set for the 17 unloaded controllers and the legacy API (`coverage.json`, `app/controllers/legacy_api/base_controller.rb:103`).
  - Add characterization tests for the 8 unloaded scheduled tasks (`coverage.json`).
  - Add a read test for the two YAML columns (`app/models/credential.rb:34`, `app/models/webhook_request.rb:37`).
  - Add a session cookie continuity test (`config/initializers/session_store.rb:5`, `config/initializers/cookies_serializer.rb:7`).
  - Add a boot check for `app/lib/smtp_server/server.rb` and `app/lib/worker/process.rb`.
- **Check:** every baseline example passes in the offline run or the run with the network on; the new tests pass on 7.1.6; the recorded set replays against 7.1.6 with no differences; web, SMTP server and worker boot.
- **Risk:** low. No version changes.
- **Effort:** 5 to 15 hours.
- **Ships separately:** yes. Depends on nothing.

### S2: Remove the annotate blocker

- **Goal:** Take `annotate` out of the bundle, or swap it for a maintained replacement, so the 8.0 and 8.1 hops resolve without a downgrade.
- **Changes:**
  - Remove or replace `gem "annotate"` at `Gemfile:54` (`registry.json` status `blocked`; `resolve.json` hops 8.0 and 8.1). We didn't look up a replacement in this run; the owner may also decide the model header comments aren't worth a tool.
  - Update or delete `lib/tasks/auto_annotate_models.rake`, which requires it at line 5 and configures it at `lib/tasks/auto_annotate_models.rake:9`, and the exclusion at `.rubocop.yml:9`.
- **Check:** `bundle lock` succeeds on 7.1.6 and, in a scratch copy, on 8.0.5.2 and 8.1.4.1 with no downgrades; no example that passed in S1 fails or is missing; `rake -T` loads.
- **Risk:** low. A development-only gem with one requiring file.
- **Effort:** 2 to 4 hours.

Assumptions:

- The suite, with the S1 additions and the recorded request set, stays the acceptance test.
- The 17 DNS-dependent examples run with the network on, as they do in CI.
- No production-only code paths exist outside what the suite and the recorded set reach.
- Dependencies behave as their declared constraints say.
- Reviews turn around within a day.
- Ruby stays at 3.4.6 and the base image stays on Debian 12.
- Gems that are majors behind but resolve on 8.1.4.1 stay at their locked versions.

What would move the number:

- A gem that fails at run time on a hop despite resolving. `chronic`, `gelf`, `nifty-utils`, `sass-rails` and `turbolinks` are the likeliest, by release date alone.
- Deprecation warnings that appear only on 7.2.4 or 8.0.5.2.
- Differences in recorded responses that need a product decision, such as JSON escaping in S8.
- A choice to re-annotate every model with a new tool in S2.
- Production configuration or data that differs from what the test environment exercises.

The range comes from a rubric whose numbers were set by judgment. It hasn't been calibrated against a completed upgrade. The low end is everything behaving as declared. The high end is each unknown named in this report costing its listed allowance. ## What can't be known without running it

- **Deprecation warnings on each hop.** The count on 7.1.6 is zero, and the harvest missed at least one known deprecation there. Warnings on 7.2.4, 8.0.5.2 and 8.1.4.1 only exist once the suite runs on those versions. Settled in S3, S4 and S5.
- **The 122 gems with no declared Rails constraint.** None depends on a Rails component, so reading their gemspecs can't settle it. The five direct gems with no release since 2019 are the sharpest case. Settled hop by hop in S3, S4 and S5.
- **Stepwise resolution.** The resolver ran each hop from today's lock. Resolving 8.0 from the 7.2 lock may pick slightly different versions. Settled in S3 to S5.
- **Early exits from transaction blocks** ([source](https://guides.rubyonrails.org/7_2_release_notes.html#active-record-removals)). The `return` and the `transaction` call are on different lines, so a line search can't pair them. From 7.2 such exits commit. Settled by reading in S3.
- **Singular associations referred to by plural name** and **durations quoted into SQL** ([source](https://guides.rubyonrails.org/7_2_release_notes.html#active-record-removals)). Both depend on run-time values. Settled in S3.
- **Adapter registration on 8.0** ([source](https://guides.rubyonrails.org/8_0_release_notes.html#active-record-removals)). Whether every database connection the app opens goes through a registered adapter shows up at boot. Settled in S4.
- **Semicolons in inbound query strings** ([source](https://guides.rubyonrails.org/8_1_release_notes.html#action-pack-removals)). This depends on the URLs clients and old tracking links send, which only access logs show. Settled in S5, and it needs log access from the owner.
- **`Time` plus `TimeWithZone` arithmetic** ([source](https://guides.rubyonrails.org/8_1_release_notes.html#active-support-removals)). The operand types are only known at run time. Settled in S5.
- **Order-dependent finders with no order, and `insert_all` through unpersisted associations** ([source](https://guides.rubyonrails.org/8_1_release_notes.html#active-record-deprecations)). Both are new deprecations on 8.1 that depend on run-time state. Settled in S5.
- **Invalid cache expiry values under the 7.1 defaults** ([source](https://guides.rubyonrails.org/configuring.html#config-active-support-raise-on-invalid-cache-expiration-time)). The values are computed at run time. Settled in S6.
- **Forward-dated migration timestamps under the 7.2 defaults** ([source](https://guides.rubyonrails.org/configuring.html#config-active-record-validate-migration-timestamps)). We expect no effect from the schema version we read, and S7 confirms it.
- **Which JSON responses change under the 8.1 escaping defaults** ([source](https://guides.rubyonrails.org/configuring.html#config-action-controller-escape-json-responses)). It depends on the data in each response. Settled in S8 against the recorded set.
- **The 40 files the suite never loads.** Coverage can't say anything about code that never ran. S1 narrows this with the recorded request set and new tests; what S1 doesn't reach stays unknown through every later stage.
- **Production-only configuration.** The suite runs from environment variables with a throwaway secret key and logging off. Real configuration files, the real secret key, Sentry, OIDC login and the production cache aren't exercised. Settled only by a staging deploy at each hop.
- **Schema and migration behavior on production-sized data.** The main database and one message database per mail server both migrate through `db:migrate` (`lib/tasks/postal.rake:43`). Timing and locking on real data can't be read from the checkout. Settled in S4 on a copy of production data, if the owner can provide one.
- **Sessions and cookies across the 7.1 defaults in production.** The S1 test holds this in the test environment. Whether logged-in users stay logged in depends on the production secret and deploy order. Settled in S6.
- **The MariaDB version.** The compose file doesn't pin one, so the version CI used and the version production runs are both unknown to us.
