### Declared behavior changes

- **Astana time zone.** Five recorded responses differ, all in the same way: in the time zone drop-down on the user settings page and the organization settings page, "Astana" moves from "(GMT+06:00)" to "(GMT+05:00)" and is listed in the new position. That is the whole difference, 10 diff lines per response. The cause is in Rails, not in this application: Active Support 7.1.6 maps the zone name "Astana" to `Asia/Dhaka`, and 7.2.4 maps it to `Asia/Almaty`. We confirmed this by reading both installed versions of `active_support/values/time_zone.rb`. The Active Support 7.2 changelog lists it as "Updating Astana with Western Kazakhstan TZInfo identifier" (https://github.com/rails/rails/blob/v7.2.4/activesupport/CHANGELOG.md). We declared the difference for exactly those five requests, on the body only, in `expected-differences.json`. It needs client sign-off because it is a real behavior change, not only a label: any user or organization whose stored `time_zone` is "Astana" will have times computed at UTC+5 instead of UTC+6 after this stage. That matches Kazakhstan's move to a single UTC+5 zone in March 2024, so the new value is the correct one, but it is a visible change for those accounts.

- **HEAD requests that end in an error page.** In production, a HEAD request for a path that does not exist gets two different response headers after this stage. `Content-Length` goes from the size of the 404 page (1564) to 0 for every client. `Content-Type` goes from `text/html; charset=UTF-8` to `*/*; charset=UTF-8` for clients that send `Accept: */*`, which is what curl, most uptime monitors and link checkers send. With a browser `Accept` header, or none, `Content-Type` stays `text/html`. The status code does not change, GET responses do not change, and HEAD requests to pages that exist do not change. The third review measured this on missing paths with puma in production on 7.1.6 and 7.2.4. The fourth review measured the 500 page as well, along with a 406 and a 404 raised by a missing record: GET is identical on both versions (1477 bytes for the 500 page), and HEAD differs in the same two headers, `Content-Length` 1477 on 7.1.6 and 0 on 7.2.4. The cause is in Rails, not in this application: since 7.2.3 the public exceptions application answers HEAD with an empty body in the format the request asked for (`action_dispatch/middleware/public_exceptions.rb` in the installed Action Pack 7.2.4). The Action Pack 7.2 changelog lists it as "Always return empty body for HEAD requests in PublicExceptions and DebugExceptions" (https://github.com/rails/rails/blob/v7.2.4/actionpack/CHANGELOG.md). The new answer is the more correct one for HEAD, and the impact is small, but it needs client sign-off for one reason: a monitor or link checker that sends HEAD to a path it expects to be missing, and reads `Content-Type` or `Content-Length` and not only the status, will see different values. Anything that reads only the status code is unaffected.

- **The Rails request log, when it is switched on.** The Rails log is off by default. It is on when `logging.rails_log_enabled` is set (`LOGGING_RAILS_LOG_ENABLED=true`), which `config/examples/development.yml` does. With it on, the line Rails writes at the end of every request changes shape. On 7.1.6: `Completed 200 OK in 39ms (Views: 26.1ms | ActiveRecord: 1.4ms | Allocations: 22156)`. On 7.2.4: `Completed 200 OK in 39ms (Views: 23.2ms | ActiveRecord: 1.1ms (1 query, 0 cached) | GC: 13.1ms)`. The `Rendered ...` lines change the same way at the end: `Allocations: N` becomes `GC: N ms`. So there are two differences: a query count is added after the Active Record time, and the allocation count is replaced by a garbage collection time. The review ran 52 production requests on each version: of 280 log lines per side, all 46 "Completed" lines and all 24 "Rendered" lines differ in this way and no other line differs. The cause is in Rails, not in this application. The query count is in the Action View 7.2 changelog as "Add queries count to template rendering instrumentation" (https://github.com/rails/rails/blob/v7.2.4/actionview/CHANGELOG.md). The replacement of the allocation count by a GC time is in none of the seven changelogs the review read, and the changelog's own example still shows `Allocations`; the source for it is the installed code, `action_controller/log_subscriber.rb` in Action Pack 7.2.4 and `active_record/railties/controller_runtime.rb` in Active Record 7.2.4, compared with the same files in 7.1.6. The application's own request log, the one `config/initializers/logging.rb` writes and that is on by default, is the same on both versions; the review compared it. No response changes. The impact is small, but it needs client sign-off for one reason: anything that feeds the Rails log to a parser, a dashboard or an alert, and reads the "Completed" or "Rendered" line beyond the status, will stop finding `Allocations` and will meet the new query count and `GC` fields.

That makes three declared changes. The first shows in five recorded requests, body only, and is declared in `expected-differences.json`. The second shows in no recorded request and cannot: the 170 recorded requests run in the test environment, where exceptions are raised and never rendered, and none is a HEAD. So it is declared here and pinned by `spec/requests/error_pages_spec.rb`, not in `expected-differences.json`. The third is not in any response at all, so no recorded request can show it either: the boot check starts the application with the Rails log on and does not read what it writes. It is declared here and pinned by `spec/requests/rails_log_spec.rb`.
